1. Product State Summary

What exists now

The app is no longer just a wireframe or front-end mock. It is a local full-stack product with portal authentication, a React operator UI, an Express API, real Postgres persistence, SMTP-backed invoice and receipt sending hooks, and Gmail-based Zelle confirmation ingestion hooks.

The portal can now function as a real internal operations surface instead of a disconnected prototype.

Primary operator surfaces

  • Login screen with session-based access control.
  • Dashboard for collected cash, outstanding balances, expected inflow, aging, and needs-attention items.
  • Billing console for due invoices, queued payments, exceptions, inbox sync, and manual invoicing.
  • Customer search across identity fields and invoice references.

3. Frontend Behavior

Operator UX requirements now reflected in the product

Login

  • Unauthenticated users see a dedicated sign-in screen before finance data loads.
  • Expired sessions return the user to login and protect the API from unauthorized requests.

Billing console

  • Status chips show schedule linkage, email readiness, and Gmail authorization state.
  • Sync Zelle inbox calls the backend Gmail sync endpoint.
  • Due invoices, payments to confirm, and exceptions update from backend state.

Manual invoice flow

  • Existing member search replaces the original static customer picker.
  • Member selection autofills identity details.
  • Service choices are constrained to member-specific services when a known member is selected.
  • New customers can still be created inline.
4. Backend Architecture

Current service layers

  1. React frontend calls /api through the Vite local proxy.
  2. Express API owns auth, invoice actions, payment confirmation, exception resolution, and inbox sync entry points.
  3. State store layer translates portal actions into transactional database operations.
  4. Service layer handles SMTP email, Gmail authorization, Gmail message parsing, and payment matching logic.
  5. Postgres acts as the source of truth for operational state.
The route layer is intentionally thin so the product can grow into more modules and APIs without business logic getting trapped in Express handlers.

6. Performance and Scale Posture

Why this backend is a better product-suite foundation

  • Postgres replaces the monolithic state blob, which is better for concurrency, queryability, and future automation.
  • Connection pooling is configurable, keeping local and small-team operating cost low while leaving room to grow.
  • Identity matching fields are normalized for predictable search and reconciliation.
  • Integration metadata uses JSON only where flexibility is helpful and query pressure is low.
  • The model can evolve toward tenant-aware organizations and workspaces without rethinking the core financial domains.
This is now shaped like the early backend of a product suite, not just a demo portal.
7. Known Limits and Next Steps

What still comes next

  • SMTP and Gmail need real credentials before external delivery and inbox sync can be validated end to end.
  • Email delivery and Gmail polling still run inline with request flow. A background jobs layer is the next performance and reliability step.
  • The portal is still single-tenant. Multi-workspace support should be the next structural evolution if this becomes a broader suite.
  • Dashboard projections are currently stored for the existing UI contract; later they can be fed by scheduled jobs or a dedicated analytics pipeline.
Recommended next product-suite move: add tenant scoping plus an outbox/job system before increasing operator count or payment volume significantly.
